# Backend e integração Angular

## Base adotada em 21/10/2026

O usuário escolheu integrar o backend de `origin/main` (`6085271`) ao layout e ao cliente HTTP locais. Há uma aplicação Spring Boot 4.0.8 com Java 21, Maven Wrapper 3.10.0, JPA/Lombok e JWT em `com.skillswap.api`. A [ADR-004](decisions/004-integra-backend-github.md) registra a escolha; a ADR-003 documenta a etapa anterior.

Os domínios de anúncios, usuários, propostas, acordos, mensagens e avaliações foram preservados. Catálogo, conta, perfil, portfólio, descoberta, propostas, acordos, conversa, reputação e moderação inicial têm integração Angular/API. Os fluxos centrais pela API e persistência após reinício passaram numa base descartável MySQL 8.0.46; o MVP ainda depende de validação MySQL 8.4, migração segura do schema legado, fluxo completo pela interface e verificações operacionais restantes.

## Convenções REST

Usar recursos nas URLs, GET sem modificar dados, POST para criação, PUT para substituição completa, PATCH para alteração parcial e DELETE para remoção autorizada. Respeitar idempotência de PUT/DELETE, DTOs, validação no servidor, filtros por query string, paginação limitada e códigos HTTP coerentes. Criação devolve 201 e Location; falhas nunca simulam sucesso.

Os aliases de autenticação recebidos do GitHub são mantidos por compatibilidade; o Angular usa as rotas de recursos abaixo. Rotas antigas dos módulos ainda sem interface deverão ser revisadas ao implementar seus fluxos, sem quebrar consumidores silenciosamente.

Os endpoints legados `/propostas/minhas`, `/propostas/recebidas`, `/propostas/{id}/aceitar`, `/propostas/{id}/recusar`, `/acordos/meus`, `/acordos/{id}/concluir` e `/acordos/{id}/cancelar` continuam disponíveis para clientes antigos. A rota legada de conclusão segue a mesma regra de confirmação mútua. O Angular usa coleções de recursos, `PATCH` no recurso e query parameters para filtrar e paginar.

O backend usa enums `MANUTENCAO`, `AULAS`, `TRANSPORTE` e `VENDA`/`TROCA`. O cliente HTTP converte os códigos para os valores internos do formulário e o envio para os enums do servidor. A média e a quantidade da oferta ignoram avaliações antigas sem `notaAnuncio`; a nota do profissional continua agregada no perfil.

Cadastro/edição: título 1–100, descrição 1–1500, cidade 1–80, categoria e modalidade válidas. Venda exige preço de 0,01 a 99.999.999,99 com até duas casas; troca exige habilidade de até 120 caracteres e não preserva preço. Campos obrigatórios rejeitam espaços. Proprietário, imagens ilustrativas, avaliações e indicação de exemplo não são controlados pelo formulário. A conta pode pausar e reativar o próprio anúncio com `PATCH`; o público vê somente anúncios ativos.

Disponibilidade: cada anúncio pode declarar até 21 combinações únicas entre os sete dias da semana e os períodos `MANHA`, `TARDE` e `NOITE`. O `PUT` substitui a lista completa e a omissão equivale a lista vazia. É uma declaração do anunciante, sem reserva ou confirmação de agenda. A migração Flyway V2 cria a tabela de associação.

Erro JSON: `{codigo,mensagem,campos}`. 400 para entrada inválida; 401 para credenciais/token ausentes ou inválidos; 403 para operação de outro usuário; 404 para recurso ausente/inativo; 405 para método indisponível; 500/503 com mensagem genérica. Não retornar SQL, senha, segredo JWT ou stack trace ao cliente.

Busca ignora acentos/caixa e trata %/_ literalmente. A pesquisa aceita categoria, cidade, modalidade e faixa de preço combinados. A faixa inclui somente vendas com valor monetário; ofertas de troca não possuem preço e não aparecem quando há filtro de preço. Um inicializador preenche o índice novo dos anúncios antigos sem mudar seus dados ou proprietários. No MySQL, outro inicializador amplia o enum antigo conhecido para incluir TRANSPORTE antes da carga; não altera enums desconhecidos. A vitrine é idempotente, identificada como ilustrativa e não substitui dados existentes. Em 28/10/2026, o validador isolado confirmou em MySQL 8.4.11 filtros combinados de categoria, cidade, modalidade, preço, texto e disponibilidade semanal, inclusive exclusão de trocas da faixa monetária e ausência de resultados quando o dia/período não coincide.

### Dados demonstrativos

A carga de `vitrine-inicial.json` contém 13 anúncios ilustrativos: os cinco originais e oito exemplos adicionais de elétrica, encanamento, pintura, inglês, reforço escolar, informática, hortas e jardinagem. Os novos exemplos ficam em Florianópolis, São José, Palhoça e Biguaçu/SC; cinco são de venda com preço/unidade e três são de troca, com habilidade desejada e preço nulo. Seus perfis são identificados como ilustrativos e não possuem notas inventadas.

Os inserts ocorrem pela aplicação/JPA no MySQL, com chave estável `codigoLegado`: reiniciar não duplica nem sobrescreve anúncios existentes. Não é necessário executar SQL manual ou criar um proprietário fictício para anúncios reais. `SEED_ENABLED=false` impede novas inserções. As coleções visuais originais permanecem preservadas como referência do layout; não são estatísticas de popularidade nem comprovam disponibilidade de produtos.

## Contas no Angular

A tela `/conta` permite registrar, entrar e sair; `/anuncios/novo` solicita login antes de salvar. O JWT fica somente em memória e é enviado apenas à API relativa da própria origem. Não há armazenamento em localStorage/sessionStorage. Recarregar encerra a sessão, mas não apaga anúncios; um 401 encerra a sessão local e a tela trata a falha.

Sair remove a credencial da memória. O token no servidor expira em uma hora; esta etapa não implementa revogação individual. A edição básica do perfil e a troca da foto usam o JWT em memória. O backend confere o conteúdo decodificado e não confia no MIME/na extensão do arquivo; SVG e WebP não são aceitos. A aplicação usa `UPLOAD_DIR` (padrão `uploads`) e os Compose local/público montam arquivos em volume ou diretório persistente. Cada conta tem quota padrão de 100 MiB (`UPLOAD_USER_QUOTA_BYTES`) e cada imagem aceita até 5 MiB; `GET /api/uploads/uso` informa o consumo, incluindo arquivos enviados ainda sem referência. A migração V6 registra fotos já ligadas a perfil, anúncio e portfólio, mede tamanhos existentes no primeiro acesso e impede contagem duplicada quando a mesma conta reenvia o mesmo conteúdo. Imagens são públicas enquanto ligadas a perfil visível, anúncio ativo não demonstrativo ou portfólio visível; sem referência pública, só a conta que enviou pode acessá-las até a limpeza. A rotina diária às 03:30 UTC remove somente arquivos hash gerados pela API, sem referência em perfil, anúncio ou publicação e com mais de 30 dias, liberando também o registro de quota. Configure `UPLOAD_ORPHAN_RETENTION_DAYS` (mínimo 1) e `UPLOAD_CLEANUP_CRON` se necessário. Os scripts `scripts/backup-uploads.sh` e `scripts/backup-mysql.sh` geram cópias verificadas por SHA-256. Em 27/10/2026, o banco público e o diretório de uploads foram verificados; não havia arquivos nem referências a `/api/uploads/`. Em 28/10, um novo dump do banco público e um arquivo do diretório de uploads foram copiados para a estação Windows, empacotados com AES-256 e conferidos por SHA-256. A chave do arquivo está protegida por DPAPI na conta Windows usada para criar o backup. A restauração do dump foi ensaiada em MySQL 8.0.46 isolado e sem rede: 7 tabelas e 44 registros; a extração do arquivo de uploads produziu zero arquivos, conforme o estado da origem. A política atual prevê 30 cópias diárias e uma cópia de fim de mês por 12 meses; a coleta, remoção e cópia ainda são manuais. A estação não é um destino externo em outro local físico ou provedor. Pagamentos integrados não estão disponíveis nesta fase.

## Limite de tentativas de autenticação

`POST /api/sessoes` e `/api/auth/login` compartilham um limite padrão de 10 tentativas por endereço IP a cada 15 minutos. `POST /api/usuarios` e `/api/auth/registrar` compartilham 5 tentativas por IP a cada hora. O limite conta todas as requisições recebidas nessas rotas, inclusive payloads inválidos e logins bem-sucedidos. Ao excedê-lo, a API responde `429 Too Many Requests`, `Retry-After` em segundos e o erro REST `{codigo,mensagem,campos}` sem armazenar o endereço em texto claro.

Configure `AUTH_RATE_LIMIT_LOGIN_MAX_ATTEMPTS`, `AUTH_RATE_LIMIT_LOGIN_WINDOW`, `AUTH_RATE_LIMIT_REGISTRATION_MAX_ATTEMPTS` e `AUTH_RATE_LIMIT_REGISTRATION_WINDOW` no ambiente. As janelas aceitam durações do Spring, como `15m` e `1h`; valores inválidos impedem a inicialização. O estado é mantido em memória por processo e limitado a 100.000 chaves ativas; com uma única instância, não sobrevive a reinícios nem sincroniza réplicas. O IP vem dos cabeçalhos encaminhados pelo proxy confiável: a API não publica sua porta e o Caddy de borda substitui valores `X-Forwarded-*` fornecidos pelo cliente. Não exponha a API diretamente nem aceite esses cabeçalhos de proxies não confiáveis.

## Backup do MySQL

`scripts/backup-mysql.sh <container-mysql> <banco> <diretorio>` gera um dump transacional com rotinas, gatilhos e eventos, compacta em gzip, valida o arquivo e grava SHA-256. O dump usa a senha de root já presente no ambiente do container, sem imprimi-la nem colocá-la nos argumentos do processo. Exemplo na VPS:

```sh
sudo ./scripts/backup-mysql.sh skillswap-mysql skillswap /home/ubuntu/backups/skillswap-mysql
```

O diretório fica com permissão `700`; arquivos e checksum, `600`. O dump usa `--single-transaction`, adequado para tabelas InnoDB; não substitui um backup coordenado se houver tabelas não transacionais. Confira o checksum antes de copiar para armazenamento externo. Antes de qualquer restauração, use outro schema/volume e compare contagens, chaves e dados. Nunca restaure diretamente sobre o banco público.

## Retenção dos backups

`scripts/reter-backups.sh <diretorio>` valida os dumps/arquivos reconhecidos e mostra a lista que seria removida, sem apagar nada. Para habilitar a retenção, primeiro restaure o backup mais recente do banco em schema MySQL isolado e extraia o arquivo de uploads em diretório temporário; compare os dados e confirme a integridade. Só depois registre essa verificação para cada arquivo mais recente:

```sh
./scripts/reter-backups.sh /home/ubuntu/backups/skillswap-mysql --confirmar-restauracao <arquivo.sql.gz>
./scripts/reter-backups.sh /home/ubuntu/backups/skillswap-uploads --confirmar-restauracao <arquivo.tar.gz>
```

Revise a simulação. Ela preserva o backup mais recente de cada dia UTC dos últimos 30 dias e o mais recente de cada mês anterior até completar 12 meses; cópias e checksums dos arquivos excedentes entram juntos na remoção. A execução real exige `--aplicar` e recusa excluir qualquer coisa se o checksum ou o formato de um arquivo falhar, ou se os marcadores não corresponderem aos backups mais recentes. Cada novo backup exige nova restauração e confirmação antes de uma poda posterior. O script não configura agendamento nem copia dados entre locais.

## Backup dos uploads

O script copia o volume Docker escolhido em modo somente leitura para um arquivo `tar.gz`, valida o arquivo, grava SHA-256 e restringe as permissões a quem executou o script. Ele não para nem altera o volume ativo. Para garantir uma cópia consistente com o banco, programe a execução em uma janela sem uploads e coordene-a com o backup do MySQL.

Confira o destino de montagem e o nome real do volume no container da API. No site público, a montagem é `/app/uploads`; não presuma o prefixo do volume Compose:

```sh
docker inspect skillswap-api --format '{{range .Mounts}}{{if eq .Destination "/app/uploads"}}{{.Name}}{{end}}{{end}}'
```

Passe o nome retornado e um diretório de backup restrito:

```sh
./scripts/backup-uploads.sh <nome-do-volume> /home/ubuntu/backups/skillswap-uploads
```

O script cria um arquivo datado e um arquivo `.sha256`. Confira o checksum antes de copiar para armazenamento externo:

```sh
cd /home/ubuntu/backups/skillswap-uploads
sha256sum -c skillswap-uploads-<data>.tar.gz.sha256
```

Antes de qualquer restauração, crie um volume descartável e valide os arquivos junto de uma cópia do banco.
